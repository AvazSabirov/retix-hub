# Retix Hub — WireGuard-сеть компаний

```
server/   FastAPI + WireGuard + iptables в Docker, SQLite, кабинеты компаний и суперадмина
client/   Python-клиент для Windows (Tkinter), сборка в RetixHub.exe
```

## Как это устроено

* Сервер — центр «звезды»: `10.66.0.1`. Каждая компания получает свою подсеть `10.66.N.0/24`.
* Клиент получает `AllowedIPs = 10.66.N.0/24, 10.66.0.1/32` — **интернет идёт мимо VPN**.
  На сервере нет NAT, а цепочка `RETIX_FWD` заканчивается `DROP` — выйти в интернет через сервер нельзя,
  даже если поменять конфиг руками.
* Между компаниями трафик запрещён. Внутри компании по умолчанию между всеми ПК разрешены ping, общие
  папки Windows (SMB, 445) и Radmin Server (4899): что открыть, решает пользователь ПК («Общий доступ» к папке).
  Галочка «любой трафик между ПК» в кабинете открывает всё внутри компании.
* База SQLite (`/root/hub/data/vpn.db` на хосте) — источник правды. При старте контейнера и каждые 5 минут
  `wg0` и iptables пересобираются из базы.
* Кабинет компании видит только свою компанию: `company_id` берётся из сессии, а не из запроса.
* Новые ПК подключаются только после одобрения («Одобрить» в списке компьютеров). Галочка «Новые ПК ждут
  одобрения» — в суперадмине (при создании компании включена, меняется на странице компании → «Параметры»)
  и в кабинете компании. Уже подключённые ПК при включении остаются в сети.
* Один вход — один компьютер: токен ПК меняется каждые 2 минуты (`TOKEN_ROTATE_SECONDS`). Если старый токен
  пришёл снова — вход скопирован на другой ПК: устройство снимается с сети и ждёт одобрения (в журнале — `token_reuse`).

## 1. Сервер

Требования: Ubuntu 20.04+ (модуль WireGuard в ядре), Docker, nginx.

Код — в `/root/hub`, данные — в `/root/hub/data` (в git не попадают).

```bash
git clone https://github.com/AvazSabirov/retix-hub.git /root/hub
cd /root/hub/server
cp .env.example .env      # укажите SUPERADMIN_PASSWORD
./run.sh                  # сборка образа и запуск контейнера (без compose)
docker logs -f retixhub  # «Retix Hub запущен, server pubkey …»
```

Обновление сервера: `cd /root/hub/server && git pull && ./run.sh` — образ пересобирается, контейнер пересоздаётся, данные в `/root/hub/data` остаются.
Остановить: `docker stop retixhub`, запустить снова: `docker start retixhub`. После перезагрузки хоста контейнер
поднимается сам (`--restart unless-stopped`).

```bash
ufw allow 51820/udp       # если включён ufw
```

nginx: API слушает только `127.0.0.1:8100`, наружу — через nginx. Конфиг `server/nginx-hub.retix.uz.conf`
(только HTTP) кладётся отдельным файлом, SSL добавляет certbot — другие сайты на сервере не затрагиваются:
```bash
cp server/nginx-hub.retix.uz.conf /etc/nginx/conf.d/hub.retix.uz.conf
nginx -t && systemctl reload nginx
certbot --nginx -d hub.retix.uz --redirect
```

Журнал сервера минимальный: только ошибки, предупреждения и строка о запуске (`docker logs retixhub`).
Запросы касс не пишутся. Docker хранит не больше 2 файлов по 5 МБ. Для разбора проблемы — `LOG_LEVEL=INFO`
(или `DEBUG` — с каждым запросом) в `.env` и `./run.sh`; потом верните `WARNING`.

Проверка на сервере:
```bash
wg show                                # интерфейс wg0 и пиры
iptables -S RETIX_FWD                   # правила между клиентами
sqlite3 /root/hub/data/vpn.db 'select login, subnet_index from companies'
```

> Если `iptables -V` на хосте показывает `legacy` — поставьте в `.env` `IPTABLES=iptables-legacy`.
> Все данные — в `/root/hub/data` на хосте (база, `server.key`, `secret.key`, `update_sign.key`, `updates/`,
> `downloads/`); другая папка — `HUB_DATA` в `.env`.
> Бэкап — это папка `/root/hub/data`. Без `server.key` всем клиентам придётся
> переподключаться, без `update_sign.key` ПК не примут новые обновления (клиент придётся поставить вручную).
>

### Адреса на hub.retix.uz

| Адрес | Что там |
|---|---|
| `https://hub.retix.uz/` | публичная страница: что такое Retix Hub, как работает, скачать клиент |
| `https://hub.retix.uz/api/...` | все запросы клиентов (справка: `/api`) |
| `https://hub.retix.uz/cabinet` | кабинет компании |
| `https://hub.retix.uz/admin` | суперадмин (ссылки на главной нет) |
| `https://hub.retix.uz/admin/updates` | суперадмин → «Обновления»: загрузка и публикация новых версий клиента |
| `https://hub.retix.uz/download/client` | скачать клиент — версия, опубликованная в «Обновлениях» для всех компаний (если нет — файл из `/root/hub/data/downloads/`) |

DNS: A-запись `hub.retix.uz` → IP сервера. SSL: см. выше (`certbot --nginx`).
Порт WireGuard (UDP 51820) идёт на тот же адрес — клиент подключается к `hub.retix.uz:51820`.

## 2. Кабинеты

* `https://hub.retix.uz/admin` — суперадмин (логин/пароль из `.env`): создаёт компании.
  У каждой два пароля: **кабинета** (для админа компании) и **подключения** (вводят в клиенте на ПК).
* `https://hub.retix.uz/cabinet` — кабинет компании: список ПК, online/offline, одобрение, блок,
  удаление, переименование, порты между ПК, смена паролей.

«Удалить» — если на ПК сохранён пароль компании, он зарегистрируется снова (при включённом одобрении — будет
ждать его). Чтобы запретить навсегда — «Блок». Чтобы выкинуть всех — смена пароля подключения с галочкой
«отключить все ПК»: ПК сразу снимаются с WireGuard и вернутся только с новым паролем.

## 3. Клиент (Windows)

Пользователям раздаётся один файл — установщик `RetixHub_Setup_<версия>.exe`. Внутри: программа,
`client_config.json` и официальный WireGuard (ставится сам, если его нет).

### Сборка в GitHub

Workflow `.github/workflows/client.yml` собирает установщик на Windows:
* push с изменениями в `client/` → установщик лежит в **Actions → запуск → Artifacts**;
* тег `v<версия>` (например `v1.0.0`) → ещё и **Releases** с установщиком.
  Тег должен совпадать с `VERSION` в `client/retixhub_client.py`.

Выпуск новой версии:
1. Поднять `VERSION` в `client/retixhub_client.py` (например `1.0.6`).
2. Дописать раздел `## 1.0.6` в `client/CHANGELOG.md` — он станет описанием релиза.
3. Влить в `main`. GitHub соберёт установщик и сам создаст **Release `v1.0.6`** с ним (3–5 минут).
4. Скачать `RetixHub_Setup_1.0.6.exe` из Release и загрузить его в **суперадмин → Обновления** →
   «Опубликовать сразу» (или по расписанию, или сначала только выбранным компаниям) — ПК обновятся сами
   (см. «Автообновление»).

Тег вручную (`git tag v1.0.3 && git push origin v1.0.3`) или Release из интерфейса GitHub тоже работают.

### Сборка на своём ПК

Нужны Windows 10/11 x64, Python 3.10+ (64-бит) и [Inno Setup 6.3+](https://jrsoftware.org/isdl.php).
```
cd client
:: при необходимости поменяйте server_url в client_config.json
build.bat
```
`build.bat`: ставит зависимости → PyInstaller (`RetixHub.spec`, onedir) → самопроверка собранного exe
(`RetixHub.exe --selftest`: Tcl/Tk, cryptography, SSL, иконка) → скачивает WireGuard MSI с проверкой подписи
(`get_wireguard.ps1`) → Inno Setup (`RetixHub.iss`). Результат: `client\dist\RetixHub_Setup_<версия>.exe`.

### Установщик

* Без вопросов: окно UAC и полоса прогресса. Обновление — тот же установщик поверх; запущенный клиент
  закрывается (VPN держит служба WireGuard, связь не рвётся). Более старую версию поверх новой не ставит.
* Ярлыки: рабочий стол и «Пуск». Автозапуск при входе в Windows включается сразу при установке
  (задача Планировщика «RetixHub» с правами администратора, окно — в трее).
* Тихая установка на много ПК: `RetixHub_Setup_<версия>.exe /VERYSILENT /SUPPRESSMSGBOXES /NORESTART`.
* Удаление (Параметры → Приложения): снимает туннель, правила firewall и автозапуск.
  WireGuard и `C:\ProgramData\RetixHub\` остаются — после повторной установки ПК вернётся в сеть сам.
* На сайт: кнопка «Скачать» отдаёт версию, опубликованную в «Обновлениях» для всех компаний. Пока таких нет —
  самый новый `RetixHub_Setup_*.exe` из `/root/hub/data/downloads/`.

### Автообновление (как у касс Retix)

**Ключ подписи.** Сервер подписывает каждую версию закрытым ключом Ed25519
(`/root/hub/data/update_sign.key`, создаётся сам). Клиент ставит только подписанный установщик. Открытый ключ
клиент запоминает при первой связи с сервером по https (`C:\ProgramData\RetixHub\state.json`) — дальше
подписанное другим ключом не ставит. Строже — зашить ключ в клиент: суперадмин → **Обновления** → «Открытый
ключ подписи» → `client/client_config.json` → `"update_public_keys": ["<ключ>"]` (тогда он главнее запомненного).
Клиенты 1.0.5 (первый вариант автообновления) переходят на новую версию сами через `/api/client/version`,
когда она опубликована «Всем компаниям»; с 1.0.4 и раньше — поставить вручную один раз.

**Выпуск.** Суперадмин → **Обновления** → загрузить `RetixHub_Setup_<версия>.exe` (до 300 МБ). Версия читается
из свойств exe (поле «Версия» — только для сверки), файл с чужим названием программы не примется, одну версию
дважды загрузить нельзя. Дальше:
* **Опубликовать сразу**, **по расписанию** (дата и время, `TZ_NAME`, по умолчанию Asia/Tashkent) или оставить
  черновиком — ПК черновик не видят;
* **кому**: всем компаниям или только выбранным (пилот на одной компании, потом «Что нового и кому» → всем);
* **Снять** с публикации — ПК, которые её ещё не поставили, больше её не берут; **Удалить** — версия и файл.
* Внизу — все ПК: версия, до чего обновиться, что сейчас (скачивает / устанавливает / не установилась).

**Как обновляется ПК.** В каждом запросе клиент шлёт свою версию и состояние (`X-Retix-Version`,
`X-Retix-Update-State`), сервер в каждом ответе — до какой версии обновиться (`X-Retix-Update`): изменилось —
клиент сразу спрашивает `GET /api/update`, иначе — раз в 10 минут. Версию, размер и SHA-256 он берёт только из
подписанного манифеста, скачивает установщик в `C:\ProgramData\RetixHub\update\` (доступ только
администраторам) с докачкой после обрыва, сверяет SHA-256 и запускает `/VERYSILENT /AUTOUPDATE=1`: установщик
ставит новую версию и запускает её (в трее). Туннель — служба WireGuard, связь не рвётся; Radmin, RDP и ping,
открытые из клиента, не закрываются. Только по https. Не встало — повтор через час, в «Обновлениях» — «не
установилась». Откатить старым файлом нельзя (установщик не ставит старую версию поверх новой) — исправление
выпускается следующей версией.

**nginx.** Загрузка больших файлов разрешена только на `/admin/updates` (`client_max_body_size 300m` в
`server/nginx-hub.retix.uz.conf`). На уже настроенном сервере (certbot уже правил конфиг) добавьте этот блок
`location = /admin/updates { … }` в `/etc/nginx/conf.d/hub.retix.uz.conf` руками, затем
`nginx -t && systemctl reload nginx` — иначе загрузка закончится ошибкой 413.

Что делает клиент:
1. Окно входа: сервер, логин компании, пароль компании, имя ПК. Ключ WireGuard генерируется на ПК,
   на сервер уходит только публичный.
2. Ставит туннель как службу Windows `WireGuardTunnel$retixhub` — VPN работает, даже если окно закрыто,
   и поднимается после перезагрузки.
3. Каждые 8 секунд проверяет сервер и handshake:
   * сервер недоступен → статус 🔴, туннель не трогает и ждёт;
   * сервер вернулся → переустанавливает туннель (заново определяет IP сервера) → 🟢;
   * нет handshake → переподключается (интервал растёт 1 → 10 мин);
   * устройство удалили / сбросили токены → сам регистрируется снова (если пароль сохранён);
   * заблокировали → снимает туннель.
4. Окно: кнопка ON/OFF, имя ПК, IP, статус; ниже — компьютеры компании
   (онлайн сверху, полоски сигнала / серый крестик). Крестик и «свернуть» прячут программу в трей (значок возле часов
   целиком зелёный / жёлтый / красный — статус), VPN работает дальше. Двойной щелчок по значку — окно.
   Повторный запуск программы (ярлык) просто показывает окно.
5. Двойной щелчок по компьютеру — его общие папки (`\\10.66.N.x`). Правый щелчок:
   * «Сообщение» — переписка с этим ПК (через сервер, только внутри компании; входящее всплывает поверх окон
     и уведомлением в трее);
   * «Копировать IP-адрес», «Пинг», «Общие папки», «Подключить сетевой диск…» (`net use` + логин через `cmdkey`);
   * «Полное управление», «Только просмотр», «Передача файлов» — Radmin Viewer подключается к Radmin Server
     на этом ПК (`Radmin.exe /connect:10.66.N.x:4899`, `/noinput`, `/file`). Порт Radmin Server **4899/TCP**
     открыт между ПК компании всегда (сервер — правило `RETIX_FWD`, клиент — firewall Windows);
     Radmin Viewer сам не слушает портов. Radmin.exe ищется в Program Files и реестре, иначе указывается один раз;
   * «Удалённый рабочий стол» — `mstsc` (RDP): на том ПК должен быть включён удалённый рабочий стол (Windows Pro),
     а в кабинете компании открыт порт 3389 (поле портов `445,3389` или «любой трафик между ПК»);
   * «Свойства» — имя, компьютер, IP, последняя связь, версия Retix Hub.
6. На каждом ПК добавляет в firewall Windows правила «RetixHub SMB» и «RetixHub Ping» (только из подсети
   компании) — иначе Windows закрывает общие папки на интерфейсе VPN. Файл `hosts` не трогает.
7. Кнопка OFF снимает туннель (и после перезагрузки остаётся выключенным), ON — подключает без пароля.
   «Система → Выйти из сети компании» — полный выход: токен отзывается и на сервере (нужен пароль подключения).
8. Не верит серверу вслепую: адреса, подсеть, ключи и порты из ответа сервера проверяются (только 10.66.0.0/16).
   Автозапуск при входе в Windows — через Планировщик заданий.

Данные клиента: `C:\ProgramData\RetixHub\` (доступ только SYSTEM и администраторам;
приватный ключ, токен и пароль зашифрованы DPAPI).
Журнал: `C:\Program Files\RetixHub\logs\client.log` (открывается без прав администратора),
аварийные падения — `crash.log` там же. В программе: «Система → Открыть журнал».

## 4. Общие папки

Как в локальной сети: все компьютеры компании видят общие папки друг друга.
1. На компьютере с папкой: правый щелчок по папке → Свойства → Доступ → Расширенная настройка →
   «Открыть общий доступ» → Разрешения.
2. Гостевой доступ в Windows 10/11 выключен — входят пользователем Windows этого компьютера
   (или создайте отдельного, например `share_user`).
3. На других ПК: двойной щелчок по компьютеру в Retix Hub — откроются его общие папки.
   Постоянный диск: правый щелчок → «Подключить сетевой диск…» → логин `pc1\share_user` и пароль.

## 5. Переход на Retix Hub

1. Поднять сервер, создать компанию, поставить клиент на PC1 и 1–2 ПК — проверить папку.
2. Поставить клиент на остальные ПК; прежний VPN держать параллельно пару дней.
3. Удалить прежний VPN.

## Тесты

```bash
pip install -r server/requirements.txt -r client/requirements.txt pytest httpx
python -m pytest tests/test_server.py tests/test_client.py -q   # 178 тестов, ~3 мин
sudo python3 tests/e2e_network.py                               # 52 проверки на настоящей сети
```

* `test_server.py` — суперадмин, регистрация, лимиты, изоляция компаний, кабинет, блок/одобрение,
  смена паролей, правила iptables, XSS/SQL-инъекции, параллельная регистрация (60 ПК одновременно).
* `test_client.py` — логика клиента против живого сервера: вход, падение/возврат сервера, потеря связи,
  удаление/блокировка/одобрение ПК, смена пароля, firewall, кнопка ON/OFF, выход.
* `e2e_network.py` — стенд из Linux network namespaces: настоящий сервер управляет WireGuard и iptables,
  4 ПК в двух компаниях. Проверяет связь, SMB к ПК с папкой, изоляцию (в т.ч. с подделанным конфигом и
  чужим IP), что интернет не идёт через VPN, перезагрузку сервера, блокировку, удаление, отключение компании.
  Нужны root, iproute2, wireguard-tools, iptables, netcat-openbsd (и модуль WireGuard или wireguard-go).

## Разработка

```bash
cd server && pip install -r requirements.txt
DATA_DIR=./devdata WG_DRY_RUN=1 COOKIE_SECURE=0 SUPERADMIN_PASSWORD=test python -m app.main
```
`WG_DRY_RUN=1` — wg и iptables не вызываются, команды только пишутся в лог.

API клиента: `POST /api/register`, `GET /api/me`, `GET /api/peers`, `POST /api/heartbeat`, `POST /api/messages`, `GET /api/messages`, `POST /api/logout`, `GET /api/ping`, `GET /api/update`, `GET /api/update/file/{id}` (по билету из `/api/update`, Range — докачка).
Ответ с заголовком `X-Retix-Token` — новый токен: клиент переходит на него сразу, старый после этого не действует.
