## 1. 🔴 Обход ограничения попыток входа → перебор пароля суперадмина

**Где:** `server/app/auth.py:51-65` (`RateLimiter`), `routers/api_client.py:158`, `routers/cabinet.py:38`,
`routers/admin.py:40-46`.

Один счётчик `limiter` по IP на три входа: `/api/register`, `/cabinet/login`, `/admin/login`. Любой **успешный** вход
делает `limiter.reset(ip)` — стирает **все** неудачи этого IP, в том числе по чужим логинам. Пароль подключения
компании знает любой сотрудник (он же сохранён на каждом ПК). Сценарий: 9 неверных паролей суперадмина → повторная
регистрация своего ПК тем же ключом (успех, счётчик обнулён) → ещё 9 → … Ограничения нет.

Пароль суперадмина сравнивается напрямую (`hmac.compare_digest`), без bcrypt — перебор идёт со скоростью HTTP-запросов.
Так же перебираются пароли кабинетов чужих компаний (их тормозит только bcrypt).

**PoC:** 60 неверных паролей `/admin/login` подряд без единого 429, затем вход — успешен.

**Последствие:** с паролем суперадмина можно загрузить и опубликовать «обновление» → см. п. 2 → код на всех ПК всех компаний.

**Исправить:**
- отдельные счётчики на каждый вход и ключ «IP + логин»; успех сбрасывает только свою пару;
- отдельный глобальный лимит для `/admin/login` (например, 5 неудач в 15 минут на всех), задержка на неудачу;
- хранить `SUPERADMIN_PASSWORD` как bcrypt-хэш, требовать длину ≥ 16;
- лучше всего — второй фактор (TOTP) для суперадмина и/или доступ к `/admin` только с белого списка IP в nginx.

## 2. 🔴 Ключ подписи обновлений хранится на сервере

**Где:** `server/app/updates.py:188-218`, `routers/updates.py:576-605`, `client/client_config.json`
(`"update_public_keys": []`), `client/retixhub_client.py:1696` (TOFU).

Сервер сам подписывает любой загруженный суперадмином exe (проверяются только `MZ`, ProductName и версия из свойств —
их задаёт кто угодно). Ключ `update_sign.key` лежит в `/data` рядом с базой. В клиенте ключ не зашит: он запоминается
при первой связи (TOFU). Значит, подпись защищает только от подмены по дороге, но не от:
- входа в суперадмин (п. 1, утечка `.env`, кража cookie);
- взлома сервера или доступа к `/data` (бэкапы, хостинг);

а установщик запускается на ПК с правами администратора (`/VERYSILENT`). Это единая точка отказа для всех ПК всех компаний.

**Исправить:**
- подписывать манифест **вне** сервера: в GitHub Actions (ключ — секрет репозитория, environment с ручным
  подтверждением) или офлайн; сервер только хранит и раздаёт готовые `manifest`+`signature`;
- зашить открытый ключ в `client_config.json` при сборке (сейчас пусто) — тогда TOFU не нужен;
- подписывать установщик Authenticode и проверять подпись в клиенте перед запуском (`WinVerifyTrust`);
- в манифест добавить привязку к релизу GitHub (тег/sha коммита) — видно, откуда exe.

## 3. 🟠 Захват ПК повторной регистрацией по открытому ключу

**Где:** `routers/api_client.py:167-180` (ветка `existing`), `services.py:299, 329` (ключи соседей в `/api/me`).

`/api/register` с уже известным `public_key` выдаёт новый токен **того же** устройства и сохраняет его одобрение,
роль и право «управляет». Владение закрытым ключом не проверяется. Открытые ключи всех соседей получают ПК компаний
с «любым трафиком» (`direct`, `direct_wan` в `/api/me`), их видно в `wg show` на любом ПК.

Сценарий: администратор любого ПК компании берёт пароль подключения (он в `state.json` под DPAPI машины) и ключ ПК
с правом «управляет» → регистрируется «им» → `/api/remote/connect` выдаёт пароли RustDesk всех ПК в режиме
«без согласия». Туннель у него не поднимется (нет закрытого ключа), но API работает. Настоящий ПК через ~8 с
пришлёт старый токен → `token_reuse` → ПК уходит в «ждёт одобрения» — пароли уже выданы. Тот же приём —
«выбить» любой ПК из сети в любой момент.

**PoC:** регистрация чужим открытым ключом → `status: active`, тот же IP, `/api/me` отвечает 200.

**Исправить:** доказательство владения ключом WireGuard. Клиент считает
`proof = HMAC-SHA256(X25519(priv_клиента, pub_сервера), "retixhub-register|" + pubkey + "|" + ts)`,
сервер — то же через свой `server.key` (у него уже есть X25519-ключ). Для существующего ключа без верного `proof`
(старые клиенты) — регистрировать, но ставить `is_approved=0` и снимать `remote_control`.

## 4. 🟠 Офис блокирует сам себя (общий счётчик)

**Где:** тот же `limiter` (п. 1).

Администратор сменил пароль подключения → 10 ПК офиса за одним NAT делают по одной неудачной регистрации → IP
офиса получает 429 на 10 минут, **включая вход администратора в кабинет** с того же IP.
**PoC:** 10 регистраций со старым паролем → `/cabinet/login` с верным паролем = 429.
Решается тем же исправлением, что п. 1 (ключ «вход + логин + IP»).

## 5. 🟠 `/api/log` блокирует цикл событий

**Где:** `routers/api_client.py:433` (`async def upload_log`) → `services.save_log` (`services.py:610`).

Обработчик асинхронный, но внутри — `threading.RLock` (`db.write_lock`) и SQLite с `busy_timeout=15 с` прямо в потоке
цикла событий. Пока другой поток держит `write_lock` (`reconcile`, п. 6) или база занята, **весь** uvicorn стоит:
ни один ПК и кабинет не получает ответ.
**Исправить:** после `await request.body()` вызывать проверку и `save_log` через `run_in_threadpool`.

## 6. 🟠 `reconcile` запускает `wg set` на каждого пира под общим локом

**Где:** `wg.py:93-98`, `services.py:687-703`.

`reconcile` идёт после каждой регистрации, выхода, действия в кабинете, `token_reuse`, раз в 5 минут — и каждый раз
запускает отдельный процесс `wg set … peer … allowed-ips` для **каждого** активного ПК, держа `write_lock`.
При сотнях ПК это секунды, всё это время другие изменения ждут. Вместе с п. 3/п. 1 (регистрация дёргает `reconcile`)
это ещё и рычаг для нагрузки.
**Исправить:** читать `wg show wg0 allowed-ips` и менять только разницу (или один `wg syncconf`/`wg addconf` из
временного файла); ограничить частоту `reconcile` (схлопывать вызовы за 1–2 с).

## 7. 🟠 Пропал `wg0` — нет самовосстановления

**Где:** `main.py` (`setup_interface` только при старте), `monitor.py:31-43`.

Если интерфейс исчез (перезапуск сети на хосте, ручной `ip link del`, сбой модуля), `reconcile` раз в 5 минут
падает с `RuntimeError` в журнал, но интерфейс не создаётся заново — все ПК без связи до `docker restart`.
**Исправить:** в мониторе проверять `ip link show wg0` и при отсутствии вызывать `wg.setup_interface()` +
`reconcile`; добавить Docker `HEALTHCHECK` (п. 17).

## 8. 🟠 `state.json` без fsync (ПК-кассы, отключение питания)

**Где:** `client/retixhub_client.py:303-314` (`_write`), `:376` (новый токен).

Файл пишется во временный и переименовывается, но без `flush`/`os.fsync`. Токен меняется каждые 2 минуты, значит и
`state.json` перезаписывается каждые 2 минуты. Выключение питания в этот момент может оставить пустой/битый файл
→ «state.json повреждён — начинаем заново» → новый ключ, нет пароля компании → ПК выпадает из сети, нужен ручной вход
(и старое устройство висит в кабинете). Если запись не удалась (`PermissionError` после 5 попыток — антивирус), токен в
памяти уже новый, на диске старый: после перезапуска старый токен → `token_reuse` → ПК «копия» и ждёт одобрения.
**Исправить:** `fsync` файла перед `replace` (и каталога), хранить `state.json.bak` и читать его при порче; при ошибке
записи нового токена — откатывать значение в памяти.

## 9. 🟡 Сессии не отзываются

**Где:** `main.py:37` (`SessionMiddleware` Starlette — подписанная cookie, без хранения на сервере).

«Выйти» только стирает cookie в браузере; украденная cookie действует до 12 часов. Смена пароля кабинета (в кабинете
или суперадмином) не завершает другие сессии; отключение компании — завершает (проверка `is_active`), это хорошо.
**Исправить:** хранить в сессии «версию пароля» (например, счётчик или часть хэша) и сверять в `current_company` /
`require_admin`; для суперадмина — дополнительно сокращённый срок.

## 10. 🟡 CSRF-токены не везде

**Где:** `web.py` (`csrf_ok`) используется только в `/admin/settings*` и `/admin/updates*`.

Остальные формы (действия с ПК, пароли, удаление компании, режим RustDesk) защищены только `SameSite=Strict`.
«Тот же сайт» для браузера — весь `*.retix.uz`: XSS или чужой контент на любом поддомене даёт CSRF в кабинеты и
суперадмин. **Исправить:** проверять `csrf` на всех POST (через зависимость роутера), токен — в `base.html`.

## 11. 🟡 Порядок правил iptables относительно Docker

**Где:** `wg.py:141-144`.

Правило `FORWARD -i wg0 -j RETIX_FWD` ставится первым один раз; если оно уже есть (`-C`), позиция не проверяется.
После перезапуска dockerd его цепочки (`DOCKER-USER`, `DOCKER-FORWARD`) встают выше, и трафик из VPN к
опубликованным портам других контейнеров на хосте может пройти раньше, чем `RETIX_FWD … DROP`.
**Исправить:** дублировать переход в `DOCKER-USER` (Docker его не трогает) или проверять, что правило — первое,
и переставлять.

## 12. 🟡 `audit_log` растёт бесконечно

**Где:** `db.py` (таблица без индекса), запись на каждое `device_reregister`, `remote_connect`, `remote_local` и др.
Кабинет ищет `WHERE company_id=? AND action='remote_connect' ORDER BY id DESC` — со временем полный просмотр.
**Исправить:** индекс `(company_id, action, id)`, хранить, например, 180 дней (чистка в мониторе раз в сутки).

## 13. 🟡 Нет заголовков безопасности, подмена текста

Нет `Strict-Transport-Security`, `X-Frame-Options`/`frame-ancestors`, `X-Content-Type-Options`, CSP
(certbot HSTS не добавляет). Параметр `?msg=` на страницах входа показывает любой текст («Позвоните по номеру…»):
XSS нет (Jinja экранирует), но фишинговая подмена — да.
**Исправить:** middleware с заголовками (или `add_header` в nginx); сообщения передавать кодом, а не текстом.

## 14. 🟡 Клиент принимает `http://`

`Worker.login` берёт адрес сервера как есть. Автообновление по `http` уже запрещено (`check`), но регистрация,
пароль компании и токены по `http` уйдут открытым текстом. **Исправить:** только `https` (кроме `127.0.0.1/localhost`).

## 15. 🟡 Память счётчика попыток

`RateLimiter.check` создаёт запись для каждого нового ключа даже без неудач — словарь растёт с каждым IP, который
когда-либо входил/регистрировался. **Исправить:** не сохранять пустой список, периодически чистить устаревшие ключи.

## 16. ⚪ Сборка и цепочка поставки

- `client/requirements.txt` — только нижние границы (`requests>=2.31` …): каждая сборка тянет новые версии, в т.ч.
  PyInstaller; сборка невоспроизводима. Нужен lock-файл с хэшами (`pip install --require-hashes`).
- Actions подключены по тегам (`@v4`, `softprops/action-gh-release@v2`), а у шага сборки есть `contents: write` и
  `GITHUB_TOKEN` в окружении `build.bat` → закрепить по SHA коммита.
- `get_rustdesk.ps1` берёт **последний** релиз RustDesk (подпись проверяется — хорошо), лучше закрепить версию.
- Установщик и `RetixHub.exe` не подписаны Authenticode (SmartScreen, нет второй линии проверки обновлений).
- В корне репозитория закоммичены `playwright-1.65.2-…whl` (53 МБ) и `greenlet-…whl` — удалить из истории или хотя бы
  из дерева и добавить `*.whl` в `.gitignore`.

## 17. ⚪ Эксплуатация

- **Бэкапы** нигде не описаны. Критичны: `vpn.db`, `server.key` (ключ WireGuard сервера), `update_sign.key`
  (потеря = ПК больше не примут обновления — TOFU), `secret.key`. Базу копировать через `sqlite3 vpn.db ".backup …"`,
  а не `cp` (WAL).
- Нет Docker `HEALTHCHECK` (например, `GET /api/ping` и наличие `wg0`) — зависание не видно.
- Один процесс uvicorn: каждый ПК делает 3 запроса за 8 с (`/me`, `/peers`, `/messages`), каждый ещё зовёт
  `updates.pick` (выборка всех выпусков). Для сотен ПК хватит; при росте — кэш выпусков и объединение запросов.

## Что сделано хорошо

- Кабинет компании берёт `company_id` только из сессии; все запросы к ПК ограничены `company_id`.
- SQL везде параметризован; f-строки — только для имён столбцов из кода.
- Клиент не доверяет серверу вслепую: `check_cfg` пускает в конфиг WireGuard и firewall только `10.66.0.0/16`,
  ключи base64, соседей — только с частными/публичными адресами по назначению; WoL — только на свою подсеть.
- Обновления: подписанный манифест Ed25519, SHA-256 и размер — только из подписи, без отката на старую версию,
  ссылка на файл — по HMAC-билету, загрузка в каталог с доступом только SYSTEM/администраторам.
- Токены ПК: хэш в базе, ротация, обнаружение копии входа; секреты на ПК под DPAPI, `%ProgramData%\RetixHub` закрыт ACL.
- Защита от zip-бомбы в `/api/log`, ограничения размеров полей (pydantic), экранирование в Telegram (`html.escape`)
  и в шаблонах (Jinja autoescape, `data-confirm` вместо JS-обработчиков).
- RustDesk: whitelist, firewall «только VPN», выключены терминал, туннели, удалённая смена настроек.
- Сервер: нет NAT, `RETIX_FWD` заканчивается `DROP`, `RETIX_IN` закрывает сервисы хоста из VPN; API только на `127.0.0.1`.

## Порядок исправления

2. п. 3 (доказательство владения ключом при повторной регистрации).
3. п. 2 (подпись обновлений в CI, зашитый открытый ключ) — требует изменений в сборке и одного ручного переходного выпуска.
4. п. 5, 7, 8 — стабильность (по небольшому изменению каждое).
5. п. 6, 9–15, затем гигиена сборки и бэкапы.
